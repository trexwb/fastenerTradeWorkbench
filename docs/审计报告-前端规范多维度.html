2维度一：功能设计审计

设计亮点（已确认事实）

  1. 模块分层清晰：core（数据/工具/UI 层）+ views（视图层）分离，符合规范"项目目录规范"中 api/components/utils 分层思想。本项目无 api 层属合理——纯本地 IndexedDB 存储，不调用外部接口（AGENTS.md §12.6"无外部 API"）。
  2. 功能覆盖完整：操作手册列出 15 大模块，覆盖紧固件贸易全链路——单位/规格/BOM/报价/订单/结算/发票/数据/AI/快捷键/搜索/知识库/自动更新。功能闭环度高。
  3. 状态机设计严谨：订单 9 态（待确认/寻货中/报价中/未成交/签约完成/送货中/异常/完成/取消）+ STATUS_FLOW 正向主线 + 分支态（未成交可恢复/异常与取消为终态），符合贸易业务实际流转。
  4. 数据存储三层架构：IndexedDB 主库 + localStorage 草稿 + File System Access 文件备份 + 独立知识库 IDB。符合"安全规范"——敏感信息不进 localStorage（仅草稿与 AI Key，AI Key 是用户主动输入的唯一例外，AGENTS.md §12.6 已明确豁免）。
  5. AI 可选增强设计优秀：写入类工具生成提案需用户逐条确认、查询类自动执行、删除走软删除、操作可整批回滚 + 并发脏读检测——企业级安全容错。
  6. JSDoc 重视度高：COVERAGE 报告显示公共函数文档覆盖率 100%（虽版本滞后但反映文档意识）。

3维度二：操作流程审计

流程亮点（已确认事实）

  1. 状态流转按钮矩阵清晰：每个状态只能上一步/下一步，严格校验（开始寻货校验产品+意向价、完成寻货校验已分配≥需求），防止跳站（操作手册 §7.4.1）。
  2. 寻货双通道：价格库匹配 + 手动录入，手动录入自动建单位/写价格库，减少重复录入。
  3. 草稿自动保存 + 恢复提示：表单未提交自动暂存，重开提示恢复或放弃。
  4. 批量操作统一模式：抽屉预览→确认→提交，不静默写入（AGENTS.md §8）。
  5. 软删除 + 回收站 + AI 无回收站权限：数据安全设计到位，AI 无法物理删除。
  6. AI 操作整批回滚 + 并发脏读检测：__beforeFingerprint 指纹对比，防确认期间数据被外部修改。
  7. 导出按状态分发模板：6 状态 6 模板（产品确认单/寻源进度单/报价单/结算单/送货单/通用），贴合贸易场景。

问题清单

P0状态回退无关联数据校验，存在孤儿数据风险

事实：操作手册 §7.4.1 明确"上一步：直接返回上一状态，不需校验"。即 prevStepOrder（orders.js:360）直接 idx-1 返回，无任何校验。

风险：从签约完成→返回报价中，或送货中→返回签约完成时，若该订单已关联结算记录（结算关联条件为"签约完成及之后各状态"）或发票任务（每笔结算生成一条发票任务），回退后：

  • 订单状态回到"报价中"，但结算记录仍存在 → 结算列表的"关联订单"查询条件（status ∈ 签约完成/送货中/完成）将查不到该订单，但结算记录的 settleId 仍引用它 → 孤儿结算。
  • 发票任务由结算生成，结算孤儿则发票也成孤儿。

建议：从签约完成/送货中回退时，校验是否已存在结算记录，有则弹窗警告"该订单已关联 N 笔结算/发票，回退将导致结算数据无法在列表中显示，是否继续？"，并记录回退原因到 aiOps。

ref: src/views/orders.js:360 prevStepOrder, docs/操作手册.md §7.4.1, docs/flows/orders.md:257-258
P1"异常"状态无人工入口，依赖 AI

事实：操作手册状态流转图显示"报价中→异常"分支，但状态流转按钮矩阵里"异常"无入口（——）。实际异常由 AI 工具 flow_order_status 进入。

影响：未启用 AI 的用户无法人工标记异常状态——而异常是处理问题的关键状态。

建议：在订单详情页状态工具栏为"报价中/签约完成/送货中"状态增加"标记异常"入口（带二次确认 + 原因填写），与 AI 路径并存。

ref: docs/操作手册.md §7.4, §13.5 工具清单 E 类 flow_order_status
P1未成交恢复与结算/发票的边界未定义

事实：未成交→恢复报价中（restoreOrderQuoting, orders.js:321）是设计的容错。但文档未说明：若未成交期间误生成了结算/发票（虽按规则未成交不在结算关联范围内），恢复后状态变化是否清理关联？结算关联条件为"签约完成/送货中/完成"，未成交本身不在内，理论上无关联，但需在代码层确认。

建议：在 restoreOrderQuoting 增加断言"该订单不应有结算关联"，并在文档明确"未成交状态不产生结算/发票"。

ref: src/views/orders.js:321 restoreOrderQuoting, docs/操作手册.md §8.1 结算关联条件

寻货入口在详情页（sourceItemFromDetail）和编辑页（sourceItem）都有，AGENTS.md §8 明确"寻货与编辑分离"约定，但两套寻货逻辑并存，维护成本高，易产生行为不一致。

问题清单

P0无暗色主题，长时间使用伤眼

事实：switchTheme（router.js:297）仅在 default（铜色）↔ cream（奶油白）两套浅色主题间切换，无 data-theme="dark" 定义。variables.css 仅有两套 :root 主题。

影响：§12.5 无障碍只提 prefers-reduced-motion，但暗色主题是现代应用基本预期，长时间浅色使用伤眼，夜间/暗光环境体验差。

建议：在 variables.css 增加第三套 [data-theme="dark"]，定义暗色背景（如 #1a1a1a）+ 浅色文字，并在 switchTheme 支持三态切换；可加 @media (prefers-color-scheme: dark) 自动识别系统偏好。

ref: src/styles/variables.css 全文, src/core/router.js:297 switchTheme
P1行内 onclick 大量存在，CSP/XSS 风险

事实：行内 onclick 是整个应用的交互范式（非 Vue SFC 模式，函数挂全局 window）——orders.js 约 58 处、prices.js 14 处、units.js 20 处等共 16 个文件。

权衡：虽偏离规范 §3"禁止行内 onclick"，但属项目既定范式（eval 全局执行模式，AGENTS.md §4 明确"业务层零算法改动 → window.* 全局语义"），是有意为之。

风险：

  • CSP 严格模式下（如 Tauri 生产）script-src 可能拦截行内事件处理器——项目记忆已记录"Tauri 构建注入 sha256 导致 unsafe-inline 失效"问题，印证此风险。
  • XSS 面扩大——若 escHtml/escAttr 在任一处遗漏，用户数据可注入 onclick 执行任意代码。

建议：① 短期——保持现状但强化 escHtml/escAttr 强制检查（可加 ESLint 规则禁止裸 innerHTML）；② 中期——逐步迁移到事件委托（document.addEventListener + data-action 属性），既保留 eval 模式又消除行内 onclick。

ref: Explore 报告 §7, 项目记忆 Tauri CSP 问题

6总结

紧固件贸易工作台是一个工程完成度极高的纯前端 SPA——功能闭环完整、状态机严谨、数据安全设计企业级、CSS 变量体系规范、AI 增强可选可回滚。在三维度审计中，功能设计与操作流程整体优秀，问题集中在文档与代码同步、文件超长拆分、状态回退关联校验三处；用户体验的主要短板是无暗色主题与行内 onclick 的 CSP 风险。

核心结论

  • 优势：数据三层存储 + 软删除 + AI 提案确认 + 整批回滚 + 脏读检测——这套组合在企业级前端中属上乘，安全容错设计可作为参考范本。
  • 短板：文档滞后于代码（版本/路径/状态枚举三处错位）、单文件超千行、无暗色主题——这三项是下一阶段改进的重点。
  • 权衡：行内 onclick、全局非响应式状态属项目既定架构（eval 全局执行 + file:// 零依赖运行），是有意为之的权衡，非缺陷，但需配套强化 escHtml 强制检查与 CSP 适配。

一句话评价

这是一个"业务逻辑扎实、安全设计精良、工程化有提升空间"的成熟项目——按阶段路线图推进 P0/P1 修复后，可达到企业级前端规范的优秀水平。
